A terminal coding agent that runs entirely on your own machine.

nave gives you the whole agentic loop — a REPL, tools, sub-agents, skills and
slash commands — and every token is generated by a model on your GPU through
[Ollama](https://ollama.com). There is no API key, no account, and no bill. Turn
off your network and it still works.

Two things make it more than a chat wrapper:

- **Per-project memory.** Each project nave works on keeps durable notes in
  `.nave/memory/`. Decisions, conventions and constraints survive between
  sessions, so the answer you get in November matches the one you got in August.
- **GPU-aware model routing.** nave reads your VRAM and each model's GGUF
  metadata, works out the largest context that actually fits, and picks a
  different model for planning, coding and summarising.

```
npm install -g nave-code
nave doctor                  # check Ollama, models, GPU, skills
cd your-project && nave init
nave
```

New here? [**INSTALL.md**](INSTALL.md) walks through Node, Ollama and your first
model with copy-paste commands for Windows (PowerShell and cmd), macOS and Linux.

Want to change nave itself? Run it from a clone instead, so your edits take
effect the moment you save: [Building from source](INSTALL.md#building-from-source).

## The memory model

This is the part worth understanding, because it is why results stay consistent.

```
your-project/
├── NAVE.md              ← standing brief, read at the start of every session
└── .nave/
    ├── memory/
    │   ├── MEMORY.md    ← generated index, injected into every system prompt
    │   └── *.md         ← one file per fact
    ├── agents/          ← your own sub-agents
    └── sessions/        ← transcripts (gitignored)
```

`NAVE.md` and `.nave/memory/` are **meant to be committed**. They are how your
team shares context with the agent. Transcripts are not — they are noise.

Every session starts with the memory index already in context. The model reads a
full entry only when it decides that entry matters, and writes a new one when it
learns something a future session would otherwise rediscover:

```
› remember that we never use the ORM's cascade delete — it bypasses the audit trigger

  ⏺ memory(no-cascade-delete)
    ⎿ memory: wrote no-cascade-delete
```

Three weeks later, in a fresh session, that constraint is already known.

Inspect it yourself with `/memory`, `/memory read <name>`, or by opening the
files — they are plain Markdown with frontmatter.

## Model routing

nave scores every installed model against nine roles (`orchestrator`, `code`,
`plan`, `review`, `explore`, `summarize`, `fast`, `vision`, `embed`) using model
family knowledge, native tool-calling support, and — crucially — whether it
actually fits in your VRAM.

```
$ nave models

MODEL                SIZE  QUANT   DISK    GPU FIT   CONTEXT  CAPABILITIES
qwen2.5-coder:7b     7.6B  Q4_K_M  4.4 GB  fits GPU  14k ctx  tools
qwen3:4b             4.0B  Q4_K_M  2.6 GB  fits GPU  32k ctx  tools thinking
qwen2.5-coder:14b   14.8B  Q4_K_M  9.0 GB  offloads   4k ctx  tools

ROLE          MODEL             WHY
orchestrator  qwen3:4b          Qwen3 affinity for orchestrator: 9; native tool calling (+4)
code          qwen2.5-coder:7b  Qwen2.5-Coder affinity for code: 9; native tool calling (+4)
```

A 14B model that spills to CPU scores *below* a 7B one that fits. Override any
role permanently:

```
nave config set models.code qwen2.5-coder:7b
```

Models without native tool calling still work — nave falls back to a text
protocol and tells you it is doing so.

## GPU optimization

`nave gpu` shows exactly where your VRAM goes and what it did about it:

```
Runtime plan for qwen2.5-coder:7b
weights          4.4 GB
KV cache         417 MB  (14k ctx @ q8_0)
compute buffers  400 MB
total            5.2 GB
budget           5.2 GB  ████████████████████
GPU layers       all

  · using free VRAM (5994 MB) minus 700 MB reserve
  · context trimmed 32768 to 14336 so weights + KV fit in 5294 MB
```

nave computes KV-cache cost per token from the model's real GGUF metadata
(layers, KV heads, head dimension) rather than guessing, then picks the largest
context that fits. If the weights alone do not fit, it calculates how many
layers to offload instead of letting the model thrash.

`nave gpu --apply` sets the Ollama server variables that materially change GPU
behaviour — flash attention, KV-cache quantisation, loaded-model limits — after
showing you each one and asking.

## Agents

The orchestrator delegates with the `task` tool. Each sub-agent gets its own
context window and its own model, so a 4B model can sweep a directory while the
7B coder keeps its context clean.

| Agent | Does |
|---|---|
| `orchestrator` | plans, delegates, verifies |
| `coder` | implements one scoped change, then checks it |
| `explorer` | read-only search — "where is X", "how does Y work" |
| `planner` | turns a vague request into an ordered plan |
| `reviewer` | finds correctness bugs and needless complexity |
| `tester` | runs builds and tests, diagnoses failures |
| `scribe` | writes project memory and docs |

Add your own as a Markdown file in `.nave/agents/`:

```markdown
---
name: migration-writer
description: Writes and verifies database migrations.
role: code
model: qwen2.5-coder:7b
tools: [read, write, edit, grep, glob, bash]
---

You write database migrations for this project. Always write the down-migration
first, and never edit a migration that has already been applied.
```

Scaffold one with `nave agents new <name>`.

## Skills

nave reads skills **in place** from three directories — `~/.claude/skills`,
`~/.nave/skills` and `.nave/skills`. Nothing is copied or imported, so a skill
you drop into any of them is live in the next session. Later sources win, which
is how a project skill shadows a user-level one of the same name.

```
$ nave skills
Skills (64)
```

The model searches and loads them itself through the `skill` tool. On models
7B and up nave also injects a compact catalogue into the system prompt; below
that it stays tool-only, because a small model handed 64 descriptions loses the
thread.

Change the sources with `skills.sources` in config.

## Tools

`read` · `write` · `edit` · `glob` · `grep` · `ls` · `bash` · `bash_readonly` ·
`todo` · `memory` · `skill` · `task` · `http`

Guardrails that matter on local models: a file must be read before it is written
or edited, paths cannot escape the project directory, and `http` refuses
anything that is not localhost or a private address — nave stays offline.

## Permissions

| Mode | Shown as | Behaviour |
|---|---|---|
| `ask` (default) | `›` | prompt before every write, edit and command |
| `acceptEdits` | `auto ›` | file changes are automatic, commands still prompt |
| `plan` | `plan ›` | read-only: investigate and propose, change nothing |
| `full` | `full ›` | never prompt |

**Shift+Tab** cycles between them mid-session, keeping whatever you had typed.
The prompt always shows the current mode, so it can never be a surprise.

Set per run with `--plan`, `--accept-edits`, `-y`, or during a session with
`/permissions`.

### Plan mode is a workflow, not just a lock

In plan mode nave investigates and then calls `present_plan`, which shows the
plan and asks:

```
╭─ plan ready ─────────────────────────────────────────────────╮
│ 1. Add a farewell function to greet.js, matching the existing style     │
│ 2. Verify by running the tests                                          │
│                                                                         │
│ [y] Approve — build it          edits apply, commands still ask         │
│ [a] Approve — no more prompts   runs to completion unattended           │
│ [n] Keep planning               stay read-only and revise               │
╚══════════════════════════════════════════════════════════════════════╝
```

Approving switches the mode and hands the mutating tools back **in the same
turn**, so the work starts immediately with the plan already in context.

One measured caveat: with a 7B model the flow works but the model often
narrates the first step instead of taking it. nave nudges twice when the todo
list still has open items, then stops. A stronger model handles it better.

### Rules

Permission rules are globs, so `bash(npm run *)` and `edit(src/**)` work as you
would expect:

```json
{ "permissions": { "allow": ["bash(npm test)", "bash(git status)"] } }
```

## Commands

**Shell**

```
nave                        interactive session
nave "<prompt>"             session with an opening request
nave -p "<prompt>"          one turn, answer on stdout (add --verbose for tool activity on stderr)
nave init                   set up NAVE.md and memory here
nave doctor                 check Ollama, models, GPU, skills, memory
nave models                 list models and how nave rates them
nave gpu [--apply]          VRAM report and server tuning
nave memory [list|read|search|rm]
nave skills [query]
nave agents [new <name>]
nave pull <model>
nave config [get|set] <path> [value]
nave sessions
```

**In session**

`/help` `/models` `/model` `/gpu` `/memory` `/agents` `/skills` `/tools`
`/permissions` `/context` `/compact` `/clear` `/sessions` `/init` `/config`
`/pull` `/exit` · **Shift+Tab** cycles permission modes

**Flags**

`-m/--model` · `--agent` · `-c/--continue` · `--resume <id>` · `--plan` ·
`--accept-edits` · `-y/--yes` · `--allow <rules>` · `--thinking` · `--verbose` ·
`--cwd <dir>` · `--no-color`

Custom slash commands are Markdown files in `.nave/commands/` or
`~/.nave/commands/`; `$ARGUMENTS` is substituted before the prompt is sent.

## Configuration

`~/.nave/config.json` for you, `.nave/config.json` per project, env last.
`nave config show` prints the merged result.

```json
{
  "ollama": { "host": "http://127.0.0.1:11434", "keepAlive": "15m" },
  "models": { "code": "qwen2.5-coder:7b", "fast": "qwen3:1.7b" },
  "gpu": { "maxContext": 32768, "reserveMb": 700, "kvCacheType": "q8_0" },
  "skills": { "sources": ["~/.claude/skills", "~/.nave/skills"] },
  "permissions": { "mode": "ask", "allow": ["bash(npm test)"] },
  "agents": { "maxDepth": 3, "maxParallel": 2, "maxSteps": 60 }
}
```

## What nave will not do

- Call a paid API, or fall back to one when a local model struggles.
- Send your code anywhere. The only network access is `nave pull`, and only
  when you ask for it.
- Claim it verified something it did not run.

[SECURITY.md](SECURITY.md) sets these out in full — what the file and `http`
tools refuse, what each permission mode actually guarantees, and which files on
disk end up shaping the instructions the model receives.

## Support

nave is free, MIT-licensed, and has no paid tier, no telemetry and nothing to
upsell. It is built on a 6 GB laptop GPU in spare time.

Three ways to help, in order of how much they actually matter:

- **Star the repository.** It costs nothing and is the main way people find a
  project like this one.

## Development

```bash
npm install          # typescript + @types/node, dev only
npm run dev          # node src/index.ts
npm run typecheck
npm run build        # optional: dist/ for faster startup
```

The wordmark nave draws at startup lives in `src/ui/logo.ts`, spelled out in
box-drawing glyphs. It used to be sampled from a PNG, which meant every terminal
cell held the average of the pixels beneath it — at terminal resolution that
reads as blur, and it got worse the further a screen recording zoomed in.
Letters are drawn by the font instead, so they stay sharp at any size and need
no colour support to be legible.

Read `NAVE.md` before changing anything — it is the brief nave itself follows in
this repo.

Contributions welcome — see [CONTRIBUTING.md](CONTRIBUTING.md) for the setup and
the rules that are load-bearing, and the [Code of Conduct](CODE_OF_CONDUCT.md)
for how we work together. Release notes are in [CHANGELOG.md](CHANGELOG.md).

Found a security problem? Please do not open a public issue — read
[SECURITY.md](SECURITY.md), which also sets out where the boundaries actually
are.
